Distributed systems · Java 21

Secure Distributed Chat.

A TLS-protected client-server chat system designed around concurrent connections, recoverable user sessions and isolation of slow clients.

Java 21TLS 1.3Virtual threads TCP socketsJUnitGradle

Challenge

Keep chat responsive when connections are slow or disappear.

A basic chat server can accept a socket and forward messages. The harder problem is handling many clients at once: one slow connection must not pause a room, and a brief network failure should not immediately erase the user's authenticated state and membership.

In a three-person team, I contributed to the initial architecture, TLS and socket communication, concurrency, session recovery, thread-safe shared state, fault tolerance, integration and debugging.

Architecture

A connection is temporary; the user session can survive it.

The client and server communicate through a small text protocol, with one command or response per line over an encrypted socket. Connection handling, authenticated commands, sessions and chat rooms are separated so network lifetime is not confused with user lifetime.

A Java virtual thread is a lightweight thread managed by the runtime. It allowed us to keep straightforward blocking socket code—one reader and one writer per client—without making one operating-system thread the practical cost of every task.

Concurrency and recovery

Queues separate room activity from network speed.

Rooms do not write directly to every socket. They update shared state, take a snapshot of recipients and place the formatted message into each session's bounded outbound queue. Dedicated writer tasks drain those queues. A slow client therefore delays its own delivery instead of holding a room lock or blocking other users.

Locking rule: protect shared room state briefly, then perform network I/O after releasing the lock.

  1. The connection breaks. The server detaches the socket but keeps the session for a limited recovery window.
  2. The client reconnects. A new TLS connection presents the secure session token.
  3. The server validates it. Expired or invalid tokens are rejected; a valid token retrieves the same user state.
  4. Delivery continues. The new connection is attached and queued messages can continue to flow.

When a queue reaches its fixed capacity, the oldest waiting item is dropped. That is a visible trade-off: bounded memory and server responsiveness take priority over unlimited delivery history for a stalled client.

Security and failure handling

Security is built into transport, credentials and session lifecycle.

Controls

  • TLS 1.3 protects client-server traffic.
  • Passwords use a per-user salt and PBKDF2 derivation.
  • Cryptographically random tokens support resume, expiry and logout.
  • Only authenticated sessions can perform room operations.

Failure boundaries

  • Heartbeat messages detect connections that silently stop responding.
  • Bounded queues prevent unlimited memory growth.
  • Expired disconnected sessions are removed periodically.
  • The optional local AI integration cannot block normal chat.

Evidence

Tests cover components; scenarios exercise the system.

JUnit tests check protocol parsing and the behaviour of the thread-safe collections and outbound queue. System scenarios exercise concurrent users, reconnection, invalid tokens, heartbeat timeouts and slow clients. GitHub Actions builds the Java 21 project and runs the Gradle checks on each change.

The most valuable evidence is the interaction between mechanisms: a session remains valid across a socket replacement, room state remains synchronized, and the writer queue prevents network I/O from entering the room's critical section.

Trade-offs

A low-level systems project, not a production chat platform.

Using sockets, locks and a custom protocol made concurrency and failure recovery visible. It also leaves deliberate limits: one central server, in-memory session state, local user persistence and no replicated room history. The TLS certificates are for local development, and the optional AI rooms require a separate local service.

A production evolution would add persistent and distributed state, stronger telemetry, a versioned protocol and fully automated end-to-end tests. Those constraints are part of the project overview: the project demonstrates the mechanics clearly without claiming a scale it did not test.
