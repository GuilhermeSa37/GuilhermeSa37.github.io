PulseFit Gym Management.

A complete gym-management application built independently to explore backend structure, authentication, multi-role workflows, relational data rules and frontend-backend integration.

PHP 8Custom MVCSQLite JavaScriptRBACJSON API

Ownership

One application covering the full request-to-database path.

PulseFit began as a university web project and became a complete independent application. I designed and implemented the routing, controllers, authentication, authorization, database layer, role-specific workflows, JSON API and browser behaviour.

I deliberately built a small MVC structure instead of starting with Laravel or Symfony. MVC—Model, View, Controller—separates data access, presentation and request coordination. Recreating those responsibilities made the request lifecycle visible and helped me understand what production frameworks normally provide.

Request lifecycle

Each request passes through explicit routing and security checks.

Every dynamic request enters through one front controller. A front controller is a single entry point that initializes the application before dispatching work. The router matches the HTTP method and path to a controller action; that action checks access, validates input, calls the data layer and returns HTML, JSON or a redirect.

  1. Resolve. The router selects the action for the request method and path.
  2. Protect. Login, role and CSRF checks run before state changes.
  3. Validate. The controller rejects invalid input and preserves useful error feedback.
  4. Execute. Prepared database queries and schema rules apply the use case.
  5. Respond. The application renders a page, redirects, or returns a consistent JSON result.

Product workflows

Members, trainers and administrators share one domain model.

Members

Manage profiles, browse schedules, enrol or cancel within capacity, review attended sessions and inspect history.

Trainers

Maintain professional information, inspect teaching schedules, manage class rosters and record attendance.

Administrators

Manage users and roles, schedule classes, assign trainers and rooms, and maintain equipment information.

Public access

Browse classes, trainers and equipment through server-rendered pages or a small read-oriented JSON API.

This range matters because authorization is not just a menu change. The server checks whether the authenticated role may perform each action, while the database protects critical relationships below the UI.

Data and security

Important rules are enforced at more than one layer.

The relational model connects users, trainer profiles, class definitions, scheduled sessions, enrolments, attendance, reviews, equipment and bookings. SQLite constraints and triggers reinforce rules that should remain true even if a controller contains a bug.

RuleWhy it exists
Class capacity cannot be exceededPrevents concurrent requests from overbooking a session.
A review requires recorded attendanceLinks feedback to a session the member actually attended.
Trainer records require the trainer rolePrevents contradictory account and domain data.
Bookings update slot availabilityKeeps schedules consistent after a reservation.

Request security

  • Hashed passwords and regenerated session identifiers.
  • Role checks on protected operations.
  • CSRF tokens on state-changing forms.
  • Prepared SQL statements and escaped HTML output.

Profile uploads

  • Maximum file-size enforcement.
  • MIME inspection instead of trusting extensions.
  • Random server-generated filenames.
  • Controlled public upload location.

API and evidence

A focused API and repeatable system checks.

The JSON API intentionally exposes only public, read-oriented information about classes, trainers and equipment. Filters and result limits are explicit, and success and error responses follow consistent shapes. It complements the product rather than pretending to be a complete versioned CRUD platform.

A scripted verification flow lints PHP source, rebuilds the sample database, validates required records, starts the application and smoke-tests public pages and API responses. It also logs in as a member, trainer and administrator using real CSRF-protected forms and checks protected routes for each role.

Testing trade-off: the system flow gives broad confidence, while focused unit and integration tests would make individual failures easier to locate.

Trade-offs

An educational framework with clearly defined limits.

Building the framework exposed routing, sessions, validation and rendering, but a production service would normally use a maintained ecosystem, structured migrations, a production database, deployment automation and operational monitoring. The built-in PHP server and SQLite setup target a local demonstration, not multiple application instances.

Production hardening would also add rate limiting, account recovery, secret management, malware scanning or image re-encoding, centralized logs and a formal security review. The value of PulseFit is the complete engineering path and explicit reasoning—not a claim that a small custom framework should replace mature tooling.
