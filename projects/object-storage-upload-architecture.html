Architecture project · 2026

Reliable object-storage upload architecture.

A proof of concept for uploading large scientific datasets directly to S3-compatible object storage, without making the application server carry every file byte.

System designS3-compatible storage Multipart uploadFastAPI OpenAPIDocker Compose

Context

Large uploads should not turn the backend into a file relay.

The original scientific platform sent datasets through the application server and kept them on its local filesystem. Long transfers therefore consumed application bandwidth and tied storage growth to the server running the product. An interrupted upload could also force the user to restart from the beginning.

Our four-person FEUP capstone explored object storage: files are stored as independent objects and accessed through an API rather than as local server files. I led the architecture and contributed substantially to the backend, database and storage integration. The public material is sanitized because the original platform is private.

A working transfer pattern, with production improvements kept separate.

  • Normal and multipart transfers.

  • Duplicate detection and explicit overwrite confirmation.

Next iteration

  • Several simultaneous resumable uploads.
  • Checksums to confirm that a reselected file is identical.
  • Automatic cleanup of abandoned uploads.
  • More complete failure, load and concurrency testing.

Architecture

The backend controls access; storage receives the bytes.

The application still authenticates the user, checks ownership, reserves a storage location and records progress. It then issues a presigned URL: a temporary link that permits one specific upload without revealing storage credentials. The browser uses that link to send the file directly to storage.

BrowserStarts and transfers the upload
BackendAuthentication, rules and upload lifecycle
Object storageReceives and keeps file bytes
DatabaseOwnership, metadata and progress
WorkersProcess raw datasets into results
Access layerAuthorizes temporary downloads

A storage adapter keeps S3-specific operations behind one backend interface. This makes the application depend on the S3-compatible API rather than on credentials or configuration from one provider. “S3-compatible” here means storage that implements the relevant Amazon S3 API operations; the prototype used a local compatible service.

Upload and recovery

Large files are divided into parts that can be retried independently.

A multipart upload splits one large file into numbered pieces. If the connection fails, only missing pieces need to be sent again. The backend stores an upload-session record so the process is not dependent on one browser tab remaining open.

  1. Create the session. The backend validates the request, checks conflicts and starts a multipart upload in storage.
  2. Request temporary links. The browser asks for URLs only for the next required parts.
  3. Transfer directly. Parts go from browser to storage while the interface reports progress.
  4. Resume safely. After a failure, the backend checks which parts storage actually has and the browser sends only the missing ones.
  5. Complete once. The backend finalizes the ordered parts, verifies the resulting object and marks the file complete.

Source of truth: browser state improves the experience, but storage and backend records decide what has really been uploaded.

Decisions

The design trades a simpler data path for a richer lifecycle.

01

Direct transfer

The backend authorizes the operation without carrying the full dataset, reducing pressure on application resources.

02

Persistent sessions

Upload progress is represented explicitly so interrupted transfers can continue rather than restart.

03

Explicit recovery

Database and storage cannot share one transaction, so retries compare both systems and bring them back into agreement.

Security boundaries

  • Authenticate and authorize every lifecycle request.
  • Limit each temporary URL to one object, operation and short time window.
  • Validate names, part numbers, sizes and checksums.
  • Keep storage credentials out of the browser.

Operational cost

  • More states and failure cases than a basic form upload.
  • Expired links must be renewed.
  • Abandoned parts require background cleanup.
  • Completion must be safe to retry after a lost response.

Evidence and limits

What this project demonstrates.

The prototype exercised complete uploads, interruption and resume, duplicate handling, overwrite confirmation and download access. More importantly, it required us to reason about ownership and consistency across a browser, a relational database and object storage.

It is not presented as production-ready. A real deployment would still need automated cleanup, stronger observability, integration tests against the chosen storage provider, failure injection and controlled large-file load tests. The full repository documents the detailed API, state model and additional trade-offs for readers who want implementation-level depth.
